# Direct video transfer trial

Open **التحكم المباشر → إرسال فيديو مباشر إلى جهاز العرض**, choose a paired device and select an MP4, WebM or MOV file (up to 512 MiB). The display must have the updated TV page open, and the sender must keep its page open and phone awake until the receiver reports ready. Select **تشغيل الفيديو على الشاشة** after receipt, or **العودة إلى العرض المعتاد** to return to the underlying show. This does not publish or replace the screen's scheduled content.

Video bytes travel over an ordered WebRTC DataChannel, in bounded 16 KiB chunks with sender backpressure. Supabase Broadcast exchanges AES-GCM encrypted connection descriptions only, using separate encryption/channel hashes of the existing private device token. File bytes are not uploaded to Supabase Storage or Cloudflare R2. Device-token possession grants access, as it already does for the linked display. Do not share device tokens.

The receiver validates file type and declared byte count, decodes the complete video, writes one cached file per screen to IndexedDB, then acknowledges readiness. A new received file replaces that screen's previous direct-transfer cache. Browser quotas and browser data deletion apply. Received bytes are assembled in memory before persistence, so large videos may exceed mobile/low-memory device limits even below 512 MiB. Actual codec support depends on the display browser; MOV is a container and not all MOV files will decode.

Play/return controls require the current transfer connection and admin tab to remain open. The file remains cached after a refresh, but this first trial does not offer a cache library or reconnect-and-play UI. The regular display continues behind the direct-video overlay and resumes when the overlay closes. Existing master volume/pause apply via MediaVideo. Global blackout remains above the overlay.

This is a **direct-connection trial**, not guaranteed cross-network delivery. Public STUN discovery is configured; a timed-out STUN lookup can still use gathered local candidates. No TURN service or relay credentials are configured. Restrictive school firewalls, carrier NAT or blocked UDP can prevent connection; the UI reports a failure/timeout rather than silently uploading the file to cloud storage. No Node process is required on the sender or receiver. Local-only mode does not expose the sender because the signaling uses hosted Supabase.

Validation: `npm run build`, `npm run lint`, `npm test`, and `node tests/peer-transfer-browser.mjs`. The browser test uses real RTCPeerConnection/DataChannel and IndexedDB, with Supabase signaling replaced by BroadcastChannel and STUN disabled so the test exercises deterministic local host candidates. It verifies exact file bytes, persistence, receiver readiness, play/return, a second transfer, and unsupported input rejection. It does not establish real cellular-to-school connectivity or verify the production Supabase broadcast configuration.
